**SSRF Logic Evaluation:**
- The alert flags "Separate DNS resolution and outbound fetch".
- In this specific code, there is indeed a separation. First, `InetAddress.getByName(name)` is called. Then later, `new java.net.URL("https://" + name + "/health").openStream()` is called using the original `name` string.
- The validation happens on the *result* of the DNS resolution (`addr`). It checks if the IP address returned by DNS is a local/private IP.
- However, the actual network request (the fetch) uses the *original hostname string* (`name`), not the validated IP address (`addr`).
- **Critical Flaw**: An attacker could provide a hostname that resolves to a private IP (passing the `isNonPublicAddress` check) OR they could exploit the fact that the second request uses the hostname string again. Wait, let's analyze the specific SSRF vector here.
- Vector 1: Attacker provides `hostname.com`. Server resolves `hostname.com` to IP X. Check passes if X is public. Then server requests `https://hostname.com/health`. This seems okay if `hostname.com` is public.
- Vector 2: Attacker provides a hostname that resolves to a private IP (like `localhost.localdomain` or something similar depending on DNS configuration). But wait, `InetAddress.getByName` will resolve it. If it resolves to a private IP, `isNonPublicAddress` returns true, and the function returns early. So direct private IPs are blocked.
- Vector 3: **DNS Rebinding**. The standard SSRF concern with this pattern ("resolve then fetch") is often DNS rebinding. The code resolves `name` once into `addr`. Then it ignores `addr` and uses `name` again in the URL construction.
    - If `name` is a domain that resolves to a public IP initially, the check passes. Then the fetch goes to that domain.
    - If `name` is a domain that resolves to a private IP initially, the check fails.
    - Is there a way to bypass?
    - Consider `name` being a CNAME chain or a hostname that triggers a redirect? No, `URL.openStream()` follows redirects usually, but the initial connection uses `name`.
    - Consider **IP Literal vs Hostname**. If `name` is an IP literal like `127.0.0.1`, `getByName` works. `isNonPublicAddress` catches it.
    - Consider **Private Domain Names**. If I pass `my-private-server.internal`, and my machine has `/etc/hosts` mapping it to `127.0.0.1`. `getByName` resolves to `127.0.0.1`. `isNonPublicAddress` returns true. Return. Safe.
    - Consider **IPv6**. Similar logic applies.
    - Consider **DNS Rebinding Attack Scenario**:
        1. Attacker sets up a malicious domain `evil.com`.
        2. Initially, `evil.com` resolves to a public IP (e.g., `8.8.8.8`).
        3. The server calls `getByName("evil.com")`. Returns `8.8.8.8`. `isNonPublicAddress` is false. Proceeds.
        4. The server constructs URL `"https://evil.com/health"` and opens stream.
        5. By the time the TCP connection is made, the attacker changes their DNS record for `evil.com` to point to `127.0.0.1` (their local machine).
        6. The client-side browser/server makes the request. Since it's a new lookup (due to TTL expiration or lack of caching in the OS stack between the two calls?), the connection hits the attacker's box.
        - **However**, the code performs `getByName` synchronously. Then immediately constructs URL. Does the JVM cache the DNS resolution? Usually yes, within the process lifetime. But `URL.openConnection()` might trigger a fresh DNS lookup if the system isn't caching aggressively or if the socket implementation forces a refresh. More importantly, `InetAddress.getByName` caches the result in the JVM's DNS cache (usually). If the JVM caches the IP, subsequent usage of the hostname in `URL` might not force a re-resolve unless explicitly told to. BUT, `URL` constructor takes a host string. When `openStream()` is called, it creates a `URLConnection`. That connection likely performs a DNS lookup.
        - Even if the DNS lookup is cached locally, the **logic flaw** described by the alert is real: validating the resolved IP does not guarantee safety against DNS rebinding attacks where the attacker controls the DNS records during the window between the validation call and the actual fetch call.
        - Furthermore, even without rebinding, simply passing a hostname allows the application to connect to whatever resource that hostname points to. While the check prevents connecting to known private IPs *as resolved*, it relies on the DNS service returning accurate info.
        - Actually, the most critical issue here is simpler: The validation checks the *resolved IP*. The fetch uses the *hostname*. If the attacker can make the hostname resolve to a private IP *during the fetch phase* but a public IP *during the validation phase* (Rebinding), the check is bypassed.
        - Additionally, some environments might have split-horizon DNS where the app sees a public IP but the internal network sees a private one, or vice versa.
        - Most importantly, relying on `isNonPublicAddress` on the resolved IP is generally considered insufficient for preventing SSRF because of the DNS Rebinding attack surface mentioned in the alert description itself ("Separate DNS resolution and outbound fetch").
        - Therefore, this is a classic SSRF vulnerability pattern. The data flows from User Input -> DNS Resolve -> Validation -> Network Fetch. The validation protects against immediate private IPs, but the separation introduces the rebinding risk.
        - Also, note that `name` is used directly in the URL string concatenation. There is no sanitization of `name` before use in the URL.
