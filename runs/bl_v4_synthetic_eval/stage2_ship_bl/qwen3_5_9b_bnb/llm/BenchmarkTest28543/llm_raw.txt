**Alert Details:**
- Rule ID: `java/ssrf`
- Message: "Separate DNS resolution and outbound fetch"
- Sink location: Line 24

**Code Analysis:**

Looking at the source code:
```java
@Override
protected void doPost(HttpServletRequest request, HttpServletResponse response)
        throws ServletException, IOException {
    response.setContentType("text/html;charset=UTF-8");
    String param = request.getParameter("BenchmarkTest");
    if (param == null) param = "";
String endpoint = param;
java.net.InetAddress resolved = java.net.InetAddress.getByName(endpoint);
byte[] octets = resolved.getAddress();
if (octets[0] == 127) return;
java.net.URLConnection c = new java.net.URL("http://" + endpoint + "/v1").openConnection();
c.connect();
}
```

**Data Flow Path:**
1. User input comes from `request.getParameter("BenchmarkTest")` → stored in `param`
2. `endpoint = param` (direct assignment)
3. `InetAddress.getByName(endpoint)` resolves the hostname to IP
4. Check if `octets[0] == 127` (loopback check)
5. If loopback check passes, create URL with `endpoint` and open connection

**Sink Resolution:**
The sink is at line 24: `new java.net.URL("http://" + endpoint + "/v1").openConnection()`

On the executed path:
- The `endpoint` variable directly equals `param` (which came from user input)
- There's a loopback check at line 19: `if (octets[0] == 127) return;`
- However, this check only prevents connections to localhost addresses (IPs starting with 127.x.x.x)
- It does NOT prevent SSRF attacks against other internal services like:
  - Private IPs (10.x.x.x, 192.168.x.x, 172.16-31.x.x)
  - Internal hostnames that resolve to private IPs
  - Localhost aliases beyond just 127.0.0.1

**Resolved Sink Value:**
The URL constructed at the sink will have `endpoint` as the hostname portion. Since `endpoint = param` and `param` comes from user input, the resolved sink value is **attacker-controlled**.

**SSRF Assessment:**
This is a classic SSRF vulnerability. The application accepts arbitrary hostnames from users, performs a basic loopback check that only covers IPv4 loopback addresses, and then makes outbound requests using those hostnames. An attacker could supply hostnames resolving to internal services (database servers, admin panels, cloud metadata endpoints) that aren't blocked by the current validation.

The loopback check provides minimal protection—it stops direct 127.x.x.x addresses but leaves numerous attack vectors open. Since the resolved sink value remains attacker-controlled throughout the execution path, this qualifies as a true positive.
