```java
protected void doPost(HttpServletRequest request, HttpServletResponse response)
        throws ServletException, IOException {
    response.setContentType("text/html;charset=UTF-8");
    String param = request.getParameter("BenchmarkTest");
    if (param == null) param = "";
String endpoint = param;
java.net.InetAddress resolved = java.net.InetAddress.getByName(endpoint);
byte[] octets = resolved.getAddress();
if (octets[0] == 127) return;
java.net.URLConnection c = new java.net.URL("http://" + endpoint + "/v1").openConnection();

```

**Data Flow Path:**
1. User input comes from `request.getParameter("BenchmarkTest")` → stored in `param`
2. `endpoint = param` (direct assignment)
3. `InetAddress.getByName(endpoint)` - DNS resolution using user-controlled endpoint
4. Check if `octets[0] == 127` (loopback check)
5. If loopback check passes, create URL with `endpoint` and open connection

**Sink Expression Resolution:**
The sink is at line 24: `new java.net.URL("http://" + endpoint + "/v1").openConnection()`

On the executed path:
- The `endpoint` variable directly receives the user parameter value
- There's a loopback check: `if (octets[0] == 127) return;`
- However, this check only verifies the FIRST octet equals 127 (localhost)
- An attacker could provide endpoints like:
  - `192.168.1.1` (internal network)
  - `10.0.0.1` (private range)
  - External IPs entirely outside localhost scope
  - Domain names resolving to internal servers

The loopback validation fails to block SSRF attacks since it only catches direct 127.x.x.x addresses while leaving numerous attack vectors viable—private ranges, external domains pointing inward, and other non-loopback targets remain accessible through the unchecked endpoint parameter.

This represents a genuine SSRF vulnerability. The resolved sink value remains attacker-controllable throughout execution, allowing arbitrary destination selection beyond localhost restrictions.
