protected void doPost(HttpServletRequest request, HttpServletResponse response)
        throws ServletException, IOException {
    response.setContentType("text/html;charset=UTF-8");
    String param = request.getParameter("BenchmarkTest");
    if (param == null) param = "";
String u = param;
if (!u.contains("127.0.0.1") && !u.contains("localhost")) {

}

**Data Flow Analysis:**

1. User input comes from `request.getParameter("BenchmarkTest")` into `param`
2. `param` is assigned to `u`
3. There's a whitelist check: `!u.contains("127.0.0.1") && !u.contains("localhost")`
4. Then `InetAddress.getByName(new java.net.URL(u).getHost())` resolves the host
5. Finally `new java.net.URL(u).openStream()` makes the actual network request

**Sink Resolution:**

The sink is at line 24: `new java.net.URL(u).openStream()`

What is the value of `u` at this point?
- `u = param` (from user input)
- The check `!u.contains("127.0.0.1") && !u.contains("localhost")` filters out some local addresses
- But this is just a string containment check, not a proper validation


- The URL gets constructed directly from `u` without further sanitization
- Even though the code checks for localhost strings, an attacker could craft URLs like `http://evil.com/127.0.0.1` or use IPv6 notation to bypass these simple substring checks
- The real issue is that the code validates the resolved address rather than the original input, creating a gap between what's checked and what's ultimately requested

This is a classic SSRF vulnerability—the application accepts arbitrary URLs, performs basic filtering that can be circumvented, and then opens streams to whatever domain the attacker specifies. The resolved sink value remains attacker-controlled throughout the execution path.

I should note there's also a potential XSS concern since the parameter flows directly to `response.setContentType()`, but that's secondary to the primary SSRF risk here.

The core vulnerability is straightforward: user-supplied input determines both the DNS lookup and the subsequent network request, with insufficient safeguards against local address exploitation.
