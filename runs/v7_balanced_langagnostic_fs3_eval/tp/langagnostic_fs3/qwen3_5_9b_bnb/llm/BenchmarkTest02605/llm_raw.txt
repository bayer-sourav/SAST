**Alert 1: `java/insecure-randomness`**
- **Rule ID:** `java/insecure-randomness`
- **Sink Line:** L101 (`String rememberMeKey = Double.toString(value).substring(2);`)
- **Source:** `nextDouble(...)` (Line 72)
- **Data Flow:** `nextDouble()` -> `toString()` -> `substring()` -> `rememberMeKey`
- **Context:** `rememberMeKey` is used later to create a Cookie and store in Session Attribute.
- **Analysis:**
    - The rule flags usage of `java.util.Random` instead of `SecureRandom`.
    - `java.util.Random` is considered cryptographically insecure for generating secrets/tokens.
    - The generated token (`rememberMeKey`) is used for authentication/session management ("Remember Me").
    - Even though the seed might vary, `java.util.Random` is known to be predictable enough to compromise session tokens if an attacker observes multiple sessions or knows the timing. OWASP guidelines explicitly recommend against using `java.util.Random` for security-sensitive purposes.
    - Does the code mitigate this? No. There is no entropy mixing or secure random generation.
    - Is the sink value controlled by attacker? No, it's generated locally. But the issue isn't about attacker control of the *value*, it's about the *quality* of the randomness being insufficient for security.
    - Wait, looking at the instruction definition for Weak Randomness/Crypto: "**alert-TP** when a predictable or weak RNG/crypto primitive feeds **session IDs, auth tokens, cookies, or other security-sensitive material** on the executed path."
    - Here, `rememberMeKey` is fed into a Cookie and Session attribute. This fits the description perfectly.
    - Therefore, **Alert 1 is alert-TP**.
