**Finding 1: `java/xss`**
*   **Sink:** `response.getWriter().println(...)` containing `org.owasp.esapi.ESAPI.encoder().encodeForHTML(fileName)`.
*   **Source:** `request.getHeader("BenchmarkTest00136")` -> `param` -> decoded -> assigned to `bar` -> concatenated into `fileName` -> passed to `encodeForHTML`.
*   **Flow:** User input via HTTP Header -> `param` variable -> `bar` variable -> `fileName` variable -> HTML encoded output.
*   **Analysis:**
    *   Input comes from `request.getHeader()`, which is user-controllable.
    *   Data flows through `URLDecoder.decode()` (removes `%XX` encodings, does not sanitize special chars like `<script>` tags).
    *   Data flows into `bar`.
    *   Switch statement determines assignment to `bar`.
    *   `switchTarget` is derived from `guess = "ABC"` and `guess.charAt(1)`. `"ABC".charAt(1)` is `'B'`.
    *   The switch cases are:
        *   Case 'A': `bar = param` (User controlled)
        *   Case 'B': `bar = "bob"` (Hardcoded safe value)
        *   Case 'C': `bar = param` (User controlled)
        *   Case 'D': `bar = param` (User controlled)
        *   Default: `bar = "bob's your uncle"` (Hardcoded safe value)
    *   Since `switchTarget` is always `'B'` (because `guess` is constant "ABC"), the execution will *always* hit `case 'B'`.
    *   In `case 'B'`, `bar` is set to `"bob"`.
    *   Therefore, `param` (which contains the potentially malicious user input) is **never used** because the branch corresponding to `param` ('A', 'C', 'D') is never reached.
    *   `bar` becomes `"bob"`.
    *   `fileName` becomes `Utils.TESTFILES_DIR + "bob"`. This is a hardcoded path segment.
    *   Finally, `fileName` is passed to `ESAPI.encoder().encodeForHTML(fileName)`. Even if `fileName` contained script tags, ESAPI encoder would encode them. However, since `fileName` is effectively hardcoded ("bob"), there is no user control reaching the sink.
    *   Conclusion: There is **no actual XSS vulnerability** on this path because the user input is blocked by the switch statement logic. It is a classic "Switch Statement Bypass" pattern often used in benchmark tests to trick scanners or demonstrate secure coding patterns where the vulnerable path is disabled.
