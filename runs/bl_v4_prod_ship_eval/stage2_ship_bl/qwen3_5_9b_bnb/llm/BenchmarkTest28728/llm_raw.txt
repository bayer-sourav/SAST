- Server stores it in session with a known key
- Client sends it back during callback

However, in this implementation, the `state` parameter itself becomes part of the session key rather than being looked up against a pre-stored value. An attacker could craft malicious requests with arbitrary state values, causing the application to look up whatever was previously stored under those crafted keys. Since these keys aren't controlled by legitimate users, they might contain unexpected or dangerous content retrieved from the session.

When `redirect` is found and begins with `/`, it gets sent back to the browser via `sendRedirect`. The critical issue is whether the lookup mechanism properly validates what's stored—there's no verification that the retrieved value matches an expected format or origin. Even though the key includes a prefix, an attacker controlling the `state` parameter could potentially trigger retrieval of sensitive session data if someone had previously stored something under a predictable key structure.

The real concern emerges when considering how OAuth state should work. Legitimate implementations generate cryptographically secure random state values on the server side and verify them during callbacks. Here, the code accepts whatever `state` parameter arrives and uses it directly as part of the lookup key without validation.
