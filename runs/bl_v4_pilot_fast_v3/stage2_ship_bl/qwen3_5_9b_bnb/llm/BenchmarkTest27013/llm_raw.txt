    *   **SSRF Logic Analysis:**
        *   Standard SSRF protection usually involves validating the destination *after* resolving, or ensuring the resolved IP isn't restricted.
        *   Here, `resolveHost(host)` is called. It converts the hostname string to an `InetAddress`.
        *   Then `isNonPublicAddress(addr)` checks if the resulting IP is private/internal.
        *   However, there is a critical flaw here often associated with DNS rebinding attacks.
        *   The check happens on the resolved IP (`addr`).
        *   But the actual connection happens using the original `host` string (`openUrlByHostname(host)` calls `new java.net.URL("https://" + host + "/health").openStream()`).
        *   Inside `URL.openConnection()` (implicitly called by `openStream`), the JVM performs DNS resolution again.
        *   **Scenario:** An attacker provides a hostname that resolves to a public IP initially (passing the `isNonPublicAddress` check), but then changes their DNS record to point to an internal/private IP (like localhost or 192.168.x.x) just before the second resolution occurs during the HTTP request. Or they provide a hostname that resolves to a public IP, passes the check, but the target service allows requests to internal resources via that hostname.
        *   More specifically, the classic "DNS Rebinding" SSRF vector relies on the fact that the validation happened on the resolved IP, but the request was made using the hostname string which might resolve differently later.
        *   Even simpler: The check `isNonPublicAddress(addr)` validates the IP returned by `resolveHost`. But `openUrlByHostname` constructs a URL with `host` and opens a stream. `URL.openStream()` triggers a new DNS lookup.
        *   Is the check sufficient?
            *   If I pass `localhost`, `resolveHost` returns 127.0.0.1. `isNonPublicAddress` returns true. Function returns early. Safe.
            *   If I pass `evil.com` which resolves to `1.2.3.4` (public). `isNonPublicAddress` returns false. Proceeds to call `openUrlByHostname("evil.com")`.
            *   Inside `openUrlByHostname`, `new java.net.URL("https://evil.com/health").openStream()` runs. This will perform a DNS lookup for `evil.com`.
            *   If the attacker controls `evil.com`'s DNS records, they could potentially make it resolve to an internal IP *during* the request time (Rebinding).
            *   Also, simply relying on the initial resolution doesn't protect against the hostname pointing to an internal resource that accepts external connections (though less likely for standard SSRF vectors compared to direct IP injection).
            *   However, the specific CodeQL rule `java/ssrf` flags "Separate DNS resolution and outbound fetch". This matches the pattern perfectly.

            *   Yes, this is a known vulnerable pattern. Validating the IP immediately after resolution but fetching via the hostname leaves a window for DNS rebinding. The fetched data comes from whatever IP `host` resolves to at the moment of the HTTP request, which might differ from the validated IP.
            *   Furthermore, even without rebinding, if the hostname resolves to a public IP that proxies to internal services, it's risky. But the primary technical issue flagged by this specific rule is the separation of resolution and usage allowing for timing-based attacks (rebinding).

            *   Since `host` is user-controllable and flows into the URL constructor, and the subsequent DNS resolution is not controlled/validated against the previous check, this is exploitable.
