**Alert Details:**
- Rule ID: `ldapi` (LDAP Injection)
- Sink location: Line 26 - `filter` variable used in `ctx.search()` call
- Message: "LDAP filter with deploy-time prefix and partial user escaping"

**Code Analysis:**

Looking at the code:
```java
String param = request.getParameter("BenchmarkTest");
if (param == null) param = "";
String prefix = getServletContext().getInitParameter("ldap.uid.prefix");
if (prefix == null) prefix = "u";
String safe = param.replace("\\", "\\5c").replace("*", "\\2a");
String filter = "(uid=" + prefix + safe + ")";
javax.naming.directory.InitialDirContext ctx =
    new javax.naming.directory.InitialDirContext();
ctx.search("ou=users", filter, null);
```

**Data Flow to Sink:**
1. User input comes from `request.getParameter("BenchmarkTest")` → stored in `param`
2. `param` goes through some replacement operations: `param.replace("\\", "\\5c").replace("*", "\\2a")` → stored in `safe`
3. `safe` is concatenated with `prefix` into `filter`
4. `filter` is passed to `ctx.search()`

**Sink Expression Resolution:**
The sink is the `filter` variable at line 26, specifically `(uid=` + prefix + safe + `)`.

On the executed path:
- `prefix` comes from either:
  - Deploy-time init parameter `"ldap.uid.prefix"` OR
  - Default fallback `"u"` if init param is null
  
- `safe` comes from `param` after replacements:
  - `param` = user input from request parameter
  - The replace operations convert `\` to `\5c` and `*` to `\2a`
  
This is a classic LDAP injection scenario. The prefix is controlled by configuration rather than user input, but the `safe` portion directly incorporates user-supplied data. Even though basic character substitutions occur, they don't comprehensively neutralize LDAP special characters like parentheses, semicolons, or logical operators that could enable injection attacks.

The core issue is that replacing just two characters leaves the rest of the payload vulnerable—attackers can craft malicious LDAP filters using other special syntax. Since the user-controlled input flows directly into the filter construction without proper sanitization, this represents a legitimate LDAP injection vulnerability.
