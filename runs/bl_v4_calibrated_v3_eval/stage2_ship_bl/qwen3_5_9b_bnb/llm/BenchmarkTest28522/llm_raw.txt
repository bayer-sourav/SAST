@Override

    response.setContentType("text/html;charset=UTF-8");

And the helper methods:
```java
private static java.net.InetAddress resolveHost(String host) throws java.net.UnknownHostException {
    return java.net.InetAddress.getByName(host);
}

private void connectHttpByHostname(String host) throws java.io.IOException {
    new java.net.URL("http://" + host).openConnection().connect();
}
```

**Data Flow Analysis:**

1. User input comes from `request.getParameter("BenchmarkTest")` → stored in `param`
2. `host = param` (line ~42)
3. `resolveHost(host)` is called - this resolves the hostname to an InetAddress
4. Check passes if address is NOT non-public (i.e., allows external addresses)
5. Then `connectHttpByHostname(host)` is called with the ORIGINAL `host` parameter

**Key Issue:** The validation happens on the RESOLVED IP address, but the actual connection uses the ORIGINAL HOSTNAME string!

This is a classic SSRF vulnerability pattern:
- The code checks if the IP address returned by DNS resolution is allowed (not loopback, site-local, link-local, etc.)


- But then it connects using the original hostname string, not the resolved IP
- An attacker could provide a hostname like `evil.com.internal.attacker.com` that resolves to a legitimate IP (passing the check) but also has CNAME records pointing to internal resources
- Or they could use DNS rebinding attacks where the initial resolution passes but subsequent requests target different IPs

**Sink Resolution:**

The sink is at line 44: `connectHttpByHostname(host)`

The `host` variable here contains the raw user input from the request parameter. Since there's no sanitization between the initial validation and the actual connection attempt, the unresolved hostname flows directly into the URL construction. Even though the IP check passes, the attack surface remains because the connection itself uses the potentially malicious hostname rather than the validated IP address.

**Verdict:**

This is a true positive. The fundamental flaw is that validating the resolved IP doesn't protect against hostname-based attacks—malicious domains can pass IP validation while still reaching internal systems through various DNS manipulation techniques. The resolved sink value is attacker-controlled since `host` originates from user input and flows directly into the connection call without being replaced by the validated IP address.

I'm confident this is a real vulnerability—the pattern matches known SSRF exploitation vectors where attackers leverage DNS mechanisms to bypass IP-based restrictions.
