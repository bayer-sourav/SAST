The sink is at line 28: `new java.net.URL("http://" + endpoint + "/v1").openConnection()`

- `endpoint = param` directly

This means the URL being fetched includes user-controlled data in the host portion!


The critical issue is that while DNS resolution occurs separately at line 25, the actual fetch at line 28 constructs the URL using the raw `endpoint` variable rather than the resolved address. An attacker could supply malicious hostnames like `evil.com.attacker.com` that pass the initial DNS lookup but redirect traffic elsewhere during the actual connection attempt. The validation only confirms the resolved IP isn't a local/private address—it doesn't verify the domain itself won't be exploited.

However, there's a potential defense mechanism worth considering. The `isNonPublicAddress` check validates against loopback, site-local, link-local, and any-local addresses. While this prevents direct localhost exploitation, sophisticated attackers might craft domains that resolve to legitimate external IPs while attempting SSRF attacks, potentially bypassing these protections depending on how the DNS records are configured.

More critically, the validation operates on the resolved IP address, not the hostname itself. An attacker could provide a domain that resolves to a public IP—passing the check—but still trigger unintended behavior through DNS manipulation or misconfigured services. Additionally, the code lacks HTTPS enforcement, allowing man-in-the-middle attacks on unencrypted connections. These factors suggest the vulnerability remains exploitable despite the apparent safeguards.

The core problem is that the validation happens too late in the chain. By checking only after DNS resolution completes, the application misses opportunities to block dangerous patterns earlier. The separation between the DNS lookup and the actual connection creates a window where crafted hostnames could slip through undetected.
